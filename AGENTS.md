# AGENTS.md

Map for working in this repo. Keep it short — it points at truth, it is not the truth.

## What this repo is

`unmapp` — an Expo SDK 57 app using expo-router. **iOS is the only target for now.**
The codebase stays cross-platform because Expo makes that free, but web is explicitly
out of scope and nothing is checked against it.

## Before you write any code

**Nothing gets implemented until User approves how it will be done.** This is a
stop, not a formality — write nothing, install nothing, edit nothing until the
answer comes back.

For anything beyond a trivial change, write an ExecPlan first, following
[docs/exec-plans/create-plan-file.md](docs/exec-plans/create-plan-file.md), put it in
`docs/exec-plans/active/`, and ask for approval. Ask the plan's open questions
_before_ presenting it, so what gets approved is the decided version.

For a change small enough not to warrant a plan — a copy fix, a renamed variable,
one obvious edit — you still say so first: state in a couple of sentences what you
are about to change and why it does not need a plan, and wait. Skipping the plan is
also User's call, not yours.

Then implement it, keeping `Progress` in the plan current as you go.

## Hard constraints

- **Expo has changed.** Read the exact versioned docs at
  <https://docs.expo.dev/versions/v57.0.0/> before writing any Expo/React Native code.
  Do not write from memory of older SDKs — APIs, config keys, and package names moved.
  This applies to installed skills too: the `building-native-ui` skill targets SDK 55
  and links v55 docs. Treat its APIs as candidates, not facts — verify each against the
  v57 docs before use.
- **Routes are files.** Anything under `src/app/` is a route. Do not put non-route
  modules there; components, hooks, and helpers go elsewhere under `src/`.
- **Native config lives in `app.config.ts`.** There is no `app.json` — the config
  is TypeScript so it can read secrets from `.env.local` instead of committing
  them. `ios/` and `android/` are generated by `npx expo prebuild` and gitignored
  — never edit or commit them; edits there are lost on the next prebuild.
- **No Expo Go.** The map is native code, so the app runs from a development
  build. Changing a native package, a config plugin, or a permission string means
  `npx expo prebuild --clean --platform ios` and a rebuild; everything else
  arrives over Fast Refresh.
- **Secrets go in `.env.local`**, never in `app.config.ts` itself and never in a
  committed file. `.env.example` documents the names. Only variables prefixed
  `EXPO_PUBLIC_` reach the app bundle — that prefix is a decision to publish the
  value, so never add it to something secret.
- **Imports use the aliases.** `@/*` -> `src/*`, `@/assets/*` -> `assets/*`,
  `@/messages/*` -> `messages/*`. No deep relative chains (`../../..`).
- **No user-visible string in a component.** The app is Polish and English. Copy
  goes in `messages/pl.json` (the source of truth for keys) and `messages/en.json`,
  and is read with `t()` from `react-i18next`. Keys are typed from `pl.json`, so a
  typo fails `npx tsc --noEmit`. See the "Language" section of [README.md](README.md).
- TypeScript is `strict`. Do not silence it with `any` or `@ts-ignore`; fix the type.

## Verify changes

```bash
npx tsc --noEmit
```

```bash
npx expo export --platform ios --output-dir /tmp/unmapp-export
```

The export proves every import and route resolves, which the type checker alone does
not. Then look at the screen you touched **on the iOS Simulator**. There are no tests
yet, so seeing it render is the check.

- **Do not verify on web.** A web check proves nothing here: it misses native text
  metrics, safe-area insets, and the splash-screen handoff.
- **Do not start the app.** A Metro instance is kept running in the background —
  attach to it. If nothing is running, say so and stop rather than starting one.

`npm run lint` (`expo lint`) is not configured yet — the first run installs and sets up
ESLint interactively.

## Keeping docs current

Canonical docs for this repo are [README.md](README.md) and this file. `docs/` holds
execution plans only — plans may link to these docs, but these docs must never link to
an individual plan, so they stay stable as plans come and go. Do not add other `docs/`
subtrees until README and this file stop answering the question.

Update them **in the same commit** as the change when it:

- adds, removes, or renames an npm script, or changes how the app is run or built;
- changes the project layout (new top-level directory under `src/`, moved routes,
  new path alias);
- changes `app.config.ts` in a way a contributor must know about (scheme, plugins,
  experiments, new native permissions);
- bumps the Expo SDK — then update the versioned docs URL in this file and in the
  README everywhere it appears;
- invalidates or adds a hard constraint above.

If a change only touches screen internals, no doc update is needed.
